# CuTile Python From First Principles — Under Development

**Writing Portable, Tile-Based GPU Kernels in NVIDIA cuTile Python, One Layer at a Time**

!!! info "This book is just getting started"
    This is the fifth sibling project to [*Mojo From First Principles*](https://maximumbeings.github.io/mojo-from-first-principles/), [*Triton From First Principles*](https://maximumbeings.github.io/triton-from-first-principles/), [*CUDA From First Principles*](https://maximumbeings.github.io/cuda-from-first-principles/), and [*Rust From First Principles*](https://maximumbeings.github.io/rust-from-first-principles/), built the same way: one chapter at a time, in page order, each one carrying real code and honestly labeled output. This book follows the Triton edition's arc rather than the CUDA/Mojo/Rust one: cuTile Python, like Triton, is a kernel-level DSL that leans on NumPy, CuPy, or PyTorch for the array itself and on PyTorch's autograd for the graph — it has no tensor type or autodiff engine of its own, and neither does this book build one. What this book owns is the tile kernel: the `@ct.kernel` functions, the tile/array type distinction, and the ahead-of-time compilation pipeline that is cuTile Python's actual point of difference from Triton. This book's verification story has its own two-tier split: every kernel definition and every ahead-of-time compilation to a named target architecture is genuinely run against the real `cuda-tile` package in this book's build environment — real cubin and Tile IR bytecode, byte-counted and shown. That environment has no NVIDIA GPU and no driver, so anything that requires an actual `ct.launch()` call against a live CUDA stream is explicitly tagged **UNVERIFIED — pending real-GPU test** rather than attempted and guessed at, until independently confirmed on real hardware and folded back in. Every chapter says plainly which of its claims rest on which kind of evidence.

> "A kernel written against CUDA C++'s SIMT model answers the question 'what does thread `(threadIdx.x, threadIdx.y, threadIdx.z)` do?' A kernel written in cuTile Python never asks that question at all — it answers a different one: 'what does block `pid` do to the tile it just loaded?' The thread grid CUDA C++ makes you reason about explicitly is still there underneath, generated by the compiler instead of typed by hand. This book is about learning to think at that higher level honestly — without pretending the lower one has vanished."

This is a practitioner's guide to cuTile Python that follows the same arc as its Triton sibling rather than its CUDA C++, Mojo, or Rust ones: instead of building a tensor type and an automatic-differentiation engine from scratch, it treats cuTile Python the way it is actually positioned — a Python DSL for writing GPU kernels, plugged into PyTorch's existing tensor and `autograd.Function` machinery through custom forward/backward kernels, the same seam the Triton book uses. Where it necessarily departs from Triton is where cuTile Python itself is different: **tiles and arrays are two distinct, statically-known types** rather than one pointer-and-stride abstraction (an `Array` is mutable, strided, lives in global memory, and supports mostly load/store; a `Tile` is immutable, has a compile-time power-of-two shape, and supports the arithmetic, `matmul`, `reduce`, and `scan` operations a kernel actually computes with); and **kernels are compiled ahead-of-time against a named target GPU architecture** (`ct.compilation.export_kernel(..., gpu_code="sm_90", ...)`) rather than JIT-specialized the way Triton kernels are, which is what makes genuine, driver-free verification possible in a sandboxed environment at all.

The design principles carried through the whole book:

- **Kernels, not a framework.** This book builds tile kernels against arrays and tensors that already exist — NumPy, CuPy, and PyTorch — the same choice the Triton edition makes and the CUDA/Mojo/Rust editions don't, because unlike those three, cuTile Python was never designed to own the tensor or the autograd graph.
- **Tiles and arrays are different types, on purpose.** Every chapter is explicit about which operations a `Tile` supports that an `Array` does not, and why: it's the single largest conceptual difference from Triton's block-pointer model, and it's introduced in Part 0 before any kernel-writing begins.
- **Portability as a genuinely tested claim, not a slogan.** The same kernel is ahead-of-time compiled in this book's own build environment to real cubin for multiple named target architectures (`sm_80`, `sm_90`, `sm_100`) with no GPU present at all — a form of real verification the CUDA book's plain `nvcc` compile doesn't have available to it, since cuTile Python's compiler resolves `libcuda.so` and any real device only at kernel-*launch* time, not at compile time.
- **Honest about verification on two different axes.** Ahead-of-time compilation to a named architecture is genuinely run and its real output byte-counted. Anything that requires launching a kernel against a live CUDA stream and reading back a real numeric result is clearly tagged unverified until tested on real hardware — this book never presents a number it didn't actually measure, or blurs the line between what compiled and what ran.
- **Financial computing ready.** The closing chapter validates these building blocks against the same kind of Black-Scholes, rolling-volatility, and Monte Carlo option-pricing problems the Mojo, Triton, CUDA, and Rust books end on.

## How the book is organized

| Part | Focus |
|---|---|
| **Part 0 — cuTile Foundations** | Arrays, tiles, and the kernel boundary; kernel parameterization with `ct.Constant`; tiled views and memory layout; the cuTile programming model (grids, `ct.bid`); targeting hardware and ahead-of-time compilation |
| **Part 1 — Kernel–Array Interface** | The array–tile contract (`ArrayConstraint`, aliasing); divisibility and alignment hints; masking, padding, and rounding modes; the memory model (order, scope, atomics); autotuning with `ct.tune` |
| **Part 2 — Core Kernels** | Elementwise kernels, the tiled matmul kernel (`ct.matmul`, tensor cores), reduction and scan kernels |
| **Part 3 — Wiring Into PyTorch's Autograd** | `torch.autograd.Function` as the graph node |
| **Part 4 — The Backward Kernel** | Writing the backward kernel, chaining custom cuTile ops through autograd |
| **Part 5 — GPU Acceleration and Performance** | Compilation and export revisited (cubin vs. Tile IR bytecode, calling conventions), benchmarking honestly with no GPU present |
| **Part 6 — Neural Network Building Blocks** | Fused kernels for real layers, interoperability (SIMT interop, JAX FFI) and advanced fusion |
| **Part 7 — Financial Computing Applications** | Black-Scholes, rolling volatility, and Monte Carlo option pricing |

Start with [Getting Started](getting-started.md) to stand up a cuTile Python environment. Part 0 (cuTile Foundations) is next up and not yet written.

!!! note "How this book relates to its siblings"
    Mojo, CUDA C++, and Rust all build their own tensor type and their own autodiff engine because none of them has anything else to lean on for this kind of from-scratch teaching arc. Triton deliberately does neither — it owns only the kernel and leans on PyTorch for the tensor, the device, and the autograd graph. cuTile Python follows Triton's arc, not Mojo/CUDA/Rust's: it has no built-in tensor abstraction and no autograd engine of its own, so this book doesn't build either — it builds kernels against PyTorch's, the same seam the Triton book uses. What's genuinely new here, with no equivalent in any of the four siblings, is the tile/array type split as a first-class language feature, and a compilation model where ahead-of-time export to a named target architecture is itself real, runnable, driver-free evidence — closer to what `nvcc` gives the CUDA book, but for a Python-hosted DSL. cuTile Python and Triton are also not unrelated projects sharing a family resemblance by accident: NVIDIA has built a Tile IR backend for Triton itself, so the same compiler infrastructure this book's kernels compile to is also, as of 2026, one of Triton's own compilation targets — a relationship this book's closing appendix examines directly, including the public disagreement between NVIDIA and Triton's original creators over it.
